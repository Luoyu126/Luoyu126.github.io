理论基础

2.1 进程：系统赋予的“独占”幻觉

进程本质上是内核提供给应用程序的两个核心抽象：逻辑控制流（让你觉得独占 CPU）和私有地址空间（让你觉得独占内存）。

逻辑控制流：

如图，物理控制流被进程A，B，C切成了3份，但在进程A，B，C看来自己拥有完整的控制流，即所谓的逻辑控制流，只是自己的逻辑控制流的指令之间存在一定的时间间隔 私有地址空间：

如图，对一个n位地址机器而言，每一个进程都认为自己拥有$0, 1, 2, \dots, 2^n - 1$地址用于存储变量等。一般而言，一个进程的内容无法轻易被其他进程读或写。（具体虚拟地址到物理地址的映射及读取等参见CSAPP） 开发者笔记：

  • 逻辑控制流决定了并发的响应性：虽然 CPU 在切换，但我们可以写出看起来“同时运行”的程序。
  • 私有地址空间决定了并发的安全性：这是多进程模型最核心的资产。因为地址空间物理隔离，子进程即便因为 Bug（如模型加载失败、内存溢出）崩溃，也绝不会污染主进程的内存。

    2.2 进程间的文件共享

在 Linux 中，“一切皆文件”。当我们说一个进程“打开了一个文件”或“建立了一个网络连接”时，内核实际上维护了三张表来管理这些资源：描述符表，打开文件表和v-node表。实际上，这三张表也是内核维护文件共享的核心处理单元。

  1. 进程级：描述符表 (Descriptor Table)
    • 所属：每个进程私有。
    • 本质：一个数组，索引就是我们常说的 fd（0, 1, 2…）。
    • 内容：每个条目指向全局“打开文件表”中的一个项。
  2. 系统级：打开文件表 (Open File Table)
    • 所属：所有进程共享。
    • 关键条目：
      • 文件位置 (File Offset)：当前的读写偏移量。
      • 引用计数 (refcnt)：当前有多少个描述符指向这个条目。

        对于回收资源极其重要

  3. 系统级：v-node 表 (v-node Table)
    • 所属：所有进程共享。
    • 内容：包含文件的静态信息（如磁盘位置、文件大小、类型等）。

  • 理解引用计数refcnt：这是理解“优雅关闭”的关键。如果子进程不 close 掉继承来的监听描述符，或者父进程不 close 掉已分发的连接描述符，内核就不会真正回收资源，最终会导致“文件描述符耗尽”报错。
  • 共享 File Offset 的风险：这是多进程并发中最隐蔽的坑。因为父子进程共享同一个偏移量，如果多个进程同时向一个文件 write，数据会发生交织。

    2.3 基于进程的并发原理：父子进程的描述符分发

下面展示了一次连接的完整生命周期：从内核描述符的角度解释了父进程是如何调度子进程完成多进程并发的。注意，此处CSAPP中提及的仅为最简化的版本，即在任务分发时已明确需要执行的任务等，实际过程中父子进程需要在分发后不断通信进行任务的分发与交付。（关于父子进程的更多基础知识见CSAPP）

为方便理解，以下用形象化的语言，把需要执行的任务定义为“客户端“，而将分发多进程的父进程定义为”服务器“。

2.3.1 服务器初始化

  • 创建 Socket：服务器进程调用 socket() 系统调用。内核在进程的描述符表中分配一个最小的可用索引（假设为 fd 3），并在内核空间创建一个对应的套接字结构。
  • 绑定与配置：通过 bind() 将 fd 3 与特定的 IP 地址和端口号关联。
  • 转换为监听状态：服务器调用 listen(3, ...)。此时，fd 3 的性质发生变化，成为监听描述符 (Listening Descriptor)。它不再负责数据传输，而是专门负责处理内核中 TCP 全连接队列里的连接请求。

2.3.2 客户端发起连接

  • 客户端初始化：客户端进程调用 socket() 创建自己的描述符（假设为 fd 5）。
  • 发起握手：客户端调用 connect(5, server_addr, ...)，内核协议栈向服务器发送 SYN 包（第一次握手）。
  • 协议栈处理：服务器内核在接收到 SYN 并完成 SYN-ACK 与 ACK（三次握手）后，将该连接从“半连接队列”移动到“已连接队列”。

2.3.3 连接的建立与分发

  • 描述符生成：服务器主进程调用 accept(3, ...)。该调用从已连接队列中取出一个条目，内核为此连接在描述符表中分配一个新的空位（假设为 fd 4）。
  • 职责分离：
    • fd 3 (监听描述符)：继续保持监听状态，负责后续其他客户端的握手请求。
    • fd 4 (已连接描述符)：代表一个具体的客户端 TCP 链接，负责该连接的数据读写。
  • 创建子进程：为了实现并发，服务器主进程调用 fork()。

2.3.4 并发处理中的描述符共享

  • 副本生成：根据 fork 机制，子进程获得父进程描述符表的完整副本。此时，子进程的描述符表中同样存在指向同一个内核文件表项的 fd 3 和 fd 4。
  • 关闭冗余句柄：
    • 子进程行为：立即执行 close(3)。因为它只负责处理当前连接，不需要监听新请求。它通过 fd 4 与客户端进行 I/O 交互。
    • 父进程行为：立即执行 close(4)。因为它已将该连接的控制权“交给”了子进程，它需要腾出资源去继续监听 fd 3。
  • 引用计数管理：内核中对应 fd 4 的打开文件表项的引用计数（refcnt）最初为 2。只有当父子进程都执行了 close 后，refcnt 归零，该物理连接才会真正被销毁。

2.3.5 父进程调度不同客户端请求

此处父进程相当于调度中心，通过将不同的描述符分发给不同的子进程分别处理不同的客户端需求。

开发者笔记：在这个模型中，父进程通过描述符分发任务，本质上是“任务状态与执行环境的完全剥离”。父进程只管“描述符/任务包”，子进程在封闭的环境里“处理计算”。这种架构天然支持多核并行，因为每个“进程”都是独立的，这为我们后面解决 Python 的 GIL 问题提供了理论基础。

2.4 线程：轻量级的逻辑流与共享

如果说进程是操作系统分配资源的最小单位，那么线程就是 CPU 调度的最小单位。

2.4.1 线程的上下文

与进程拥有庞大的私有地址空间不同，线程非常轻量，只拥有维持运行所必须的极少量私有数据：

  • 线程 ID (TID)：每个线程的唯一标识。
  • 程序计数器 (PC)：记录当前执行到的指令位置。
  • 寄存器与栈指针：存储临时变量和函数调用记录。

2.4.2 共享、透明的内存空间

在同一个进程内的多个线程，就像是在同一个办公室里共用资料库的员工。它们共享：

  • 整个虚拟地址空间：包括只读的代码段、读/写数据段、以及堆。这意味着一个线程创建的对象，其他线程可以直接读写。

  • 打开的文件集合：所有的文件描述符对所有线程是完全透明共享的。

  • 开发者笔记：
    • 低开销及代价：线程的创建比进程快得多，因为不需要复制页表（进程的私有地址空间在触发写操作时需要通过复制页表实现，但如果只是读操作会触发COW机制延迟复制）。但这种“零距离”共享意味着一个线程写坏了内存，整个进程都会挂掉。
    • 通信零成本：线程间通信不需要像多进程那样搞 IPC（管道/队列），直接读写全局变量即可。但也正是这种便利，我们需要花费更多的精力和运行时间去安排“竞争”

      2.5 变量映射与同步风险

由于线程间内存是共用的，资源的管理变得极其复杂。

  • 竞争条件：由于多线程可以同时访问相同内存，即使是 count += 1 这样简单的操作，在 CPU 层面也涉及“读-改-写”三步。如果没有同步，两个线程可能同时读到旧值，导致更新丢失。

  • 同步元语：为了解决竞争，必须引入互斥锁。（关于互斥锁更详细的内容参见CSAPP信号量一节）

  • 开发者笔记：
    • 锁争用：在一个进程内开启多个线程时，如果它们都在抢同一把锁，多个线程会处于阻塞状态。并行的代码实际上退化成了串行。
    • 不可见的性能税：加锁、解锁、以及内核在不同线程间疯狂切换，会消耗大量 CPU 时钟周期。

2.6 Python 的特殊枷锁：GIL (Global Interpreter Lock)

这把GIL锁就是2.5中提到的互斥锁，也是我在实验中遇到的耗时飙升的底层根源：

  • 核心限制：为了内存安全，CPython 解释器要求在任何时刻，一个进程中只有一个线程能持有 GIL 执行 Python 字节码。
  • CPU 密集型困境：在进行计算（涉及大量正则匹配、HTML 解析）时，线程会死死攥住 GIL 不放。

  • 性能退化：多个线程抢夺唯一的 GIL，产生巨大的上下文切换开销。这种“伪并行”不仅无法利用多核 CPU，反而因为内耗导致单位样本处理速度显著退化。

  • 开发者笔记：
    • 识别任务类型：这是方法论的核心。如果你的任务是 time.sleep() 或等待网络 API 返回（I/O 密集），多线程是神药；如果是疯狂算逻辑的任务（CPU 密集），多线程就是毒药

实例分析：从“几乎卡死”到“秒速处理”

在昨天的场景中，优化的核心任务大致可以理解为：对2w条模型输出进行归一化并根据模型输出和gt计算某种得分。这是一个典型的计算密集型（CPU-bound）任务，对 CPU 算力有着极高的连续需求。

演进路线：三种计算模型的客观实验

在尝试中我先后尝试了以下三种方法，分别对应不同的系统级处理逻辑与资源分配方式。

阶段 A：串行流

  • 运行机制：采用标准 for row in rows 循环。程序在单一逻辑控制流下运行，指令按序进入 CPU。
  • 资源利用：仅占用 1 个 CPU 核心，其余 15 核处于“围观”状态。
  • 实际表现：
    • 平均耗时：1.76s / 样本。
    • 评价：逻辑最简单，但面对近 2 万条数据，预估总耗时超过 8 小时，无法满足快速迭代的需求。

阶段 B：多线程

  • 尝试：使用 ThreadPoolExecutor，试图通过 64 个并发线程来切分任务，并为每个线程准备了私有的计算实例用来计算gt和模型回复之间的匹配程度。

    这里我当时天真的以为max_workers开的越大就应该越快吧 [🤦]

  • 核心矛盾（GIL 枷锁）：
    • 计算涉及大量的正则匹配与矩阵运算，属于 Python 字节码密集操作，无法触发 GIL 的自动释放。
    • 16 个物理核心上的 64 个线程在内核中疯狂争夺唯一的 GIL 锁。
  • 实际表现：
    • 平均耗时：96.1926s / 样本。
    • 现象：性能发生严重退化，单条耗时相比串行反而慢了约 200 倍。系统 99% 的能量消耗在了“为了抢锁而进行的无效上下文切换”上。
    • 分析：在 CPU 密集任务中，由于线程无法主动交出锁，OS 会频繁强制切换线程。每一次切换都要保存/恢复寄存器、刷新缓存，这在 64 个线程的高并发下会产生“惊群效应”。即多线程阶段的高耗时并非 CPU 算力不足，而是 99% 的时间都浪费在了 L3 Cache 的频繁失效和内核态/用户态的无意义切换上。

阶段 C：多进程——真正释放多核福利

  • 策略：切换为 ProcessPoolExecutor，开启 16 个独立的 worker 进程。
  • 技术优势（内核级对齐）：
    • 绕过 GIL：每个进程拥有独立的 Python 解释器和 GIL，16 个核心真正实现了真并行。
    • 内存优化：利用 initializer 进行进程级一次性初始化，并配合 COW (写时复制) 机制，确保了高效的资源利用。
    • I/O 收口：针对 File Offset 共享 风险，设计了“子进程只传变量，主进程统一写盘”的模式，规避了并发写导致的文件损坏。
  • 实际表现：
    • 平均耗时：2.21s / 样本。
    • 吞吐量：内核同时启动16个进程，吞吐量约0.14s / 样本，吞吐量显著提升，耗时分布恢复正常，整体处理速度相比串行提升了约 10-12 倍。
    • 进程间通信：多进程的单条耗时略增（1.7s -> 2.2s），是由于主进程需要将数据 Pickle 序列化后通过管道（Pipe）传输给子进程。（相比于ICS课本中提到的父进程接收到信号即可分发好对应数据的模型，现实使用中更多是需要父进程动态分发数据给不同的子进程去处理，之后子进程将处理好的数据返还给父进程）

方法总结：多线程还是多进程？

通过以上的分析，我们可以总结出一套在 Python 环境下选择并发模型的通用方法论。

3.1 核心判断矩阵

选择并发模型的第一步，是识别任务的“性能瓶颈”在哪里：

维度 多线程 多进程
瓶颈定位 I/O 密集型 CPU 密集型
典型场景 爬虫、API 请求、数据库读写、文件下载 大模型计算、图像处理、复杂正则匹配
通信成本 极低（共享进程内存，直接读写变量） 较高（需跨进程序列化，通过 Queue/Pipe 通信）
安全性 较低（一者崩则全家崩；存在竞争风险） 极高（物理隔离，子进程崩溃不影响主进程）
Python 限制 受限于单 GIL（16 核也只能跑 1 核速度） 绕过 GIL（真正实现多核并行）

3.2 决策算法：三步走指南

当你面对一个需要加速的任务时，请按以下顺序自问：

第一步：代码里有没有“等”的操作？

  • 如果在执行过程中，CPU 大部分时间在等待网络回包、磁盘 I/O 或 time.sleep()，请首选 多线程。
  • 理由：线程切换极快，且在等待时会自动释放 GIL，让出执行权。

第二步：逻辑里有没有“算”的操作？

  • 如果代码在疯狂进行循环运算、矩阵解析或大量文本处理，请务必选择多进程。
  • 理由：计算任务不会主动交出 GIL。在单 GIL 下加线程，只会导致 2.5 节所说的“指令级冲突”和“锁争用”。

第三步：数据是否需要“写回”？

  • 如果多个并发单元需要修改同一个全局字典或写入同一个文件：
    • 多线程：必须加 Mutex（互斥锁），但这会进一步拖慢 CPU 密集任务。
    • 多进程：推荐采用 “分布式计算 + 主进程聚合” 模式。让子进程只管计算并返回结果，由主进程负责唯一的 I/O 操作。

3.3 避坑避雷指南

  1. 不要迷信“线程轻量”： 在 Python 里，线程确实比进程省内存，但在 CPU 密集任务面前，多出的那点内存开销远比不上 200 倍的性能退化（如本次实验中的 99s 惨案）。

  2. 利用 COW (写时复制) 优化进程初始化： 在面对计算实例这种大型对象时，利用 multiprocessing 的 initializer 在 fork 瞬间进行“逻辑共享、物理隔离”的加载，是兼顾内存与速度的最优解。

  3. 警惕文件偏移量共享： 牢记 2.2 节的理论：文件位置是系统级共享的。始终坚持由主进程单点写盘，或为每个子进程分配独立的临时文件。
