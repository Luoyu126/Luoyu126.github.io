理论基础

1.1 进程：系统赋予的“独占”幻觉

进程本质上是内核提供给应用程序的两个核心抽象：逻辑控制流（让你觉得独占 CPU）和私有地址空间（让你觉得独占内存）。

逻辑控制流：

如图，物理控制流被进程 A、B、C 切成了 3 份，但在进程 A、B、C 看来自己拥有完整的控制流，即所谓的逻辑控制流，只是自己的逻辑控制流指令之间存在一定的时间间隔。

私有地址空间：

如图，对一个 n 位地址机器而言，每一个进程都认为自己拥有 $0, 1, 2, \dots, 2^n - 1$ 地址用于存储变量等。一般而言，一个进程的内容无法轻易被其他进程读或写。（具体虚拟地址到物理地址的映射及读取等参见 CSAPP）

开发者笔记：

  • 逻辑控制流决定了并发的响应性：虽然 CPU 在切换，但我们可以写出看起来“同时运行”的程序。
  • 私有地址空间决定了并发的安全性：这是多进程模型最核心的资产。因为地址空间物理隔离，子进程即便因为 Bug（如模型加载失败、内存溢出）崩溃，也绝不会污染主进程的内存。

1.2 进程间的文件共享

在 Linux 中，“一切皆文件”。当我们说一个进程“打开了一个文件”或“建立了一个网络连接”时，内核实际上维护了三张表来管理这些资源：描述符表、打开文件表和 v-node 表。实际上，这三张表也是内核维护文件共享的核心处理单元。

  1. 进程级：描述符表 (Descriptor Table)
    • 所属：每个进程私有。
    • 本质：一个数组，索引就是我们常说的 fd（0, 1, 2…）。
    • 内容：每个条目指向全局“打开文件表”中的一个项。
  2. 系统级：打开文件表 (Open File Table)
    • 所属：所有进程共享。
    • 关键条目：
      • 文件位置 (File Offset)：当前的读写偏移量。
      • 引用计数 (refcnt)：当前有多少个描述符指向这个条目。
  3. 系统级：v-node 表 (v-node Table)
    • 所属：所有进程共享。
    • 内容：包含文件的静态信息（如磁盘位置、文件大小、类型等）。

开发者笔记：

  • 理解引用计数 refcnt：这是理解“优雅关闭”的关键。如果子进程不 close 掉继承来的监听描述符，或者父进程不 close 掉已分发的连接描述符，内核就不会真正回收资源，最终会导致“文件描述符耗尽”报错。
  • 共享 File Offset 的风险：这是多进程并发中最隐蔽的坑。因为父子进程共享同一个偏移量，如果多个进程同时向一个文件 write，数据会发生交织。

1.3 基于进程的并发原理：父子进程的描述符分发

下面展示了一次连接的完整生命周期：从内核描述符的角度解释了父进程是如何调度子进程完成多进程并发的。注意，此处 CSAPP 中提及的仅为最简化版本，即在任务分发时已明确需要执行的任务。实际过程中父子进程需要在分发后不断通信进行任务的分发与交付。（关于父子进程的更多基础知识见 CSAPP）

为方便理解，以下用形象化语言，把需要执行的任务定义为“客户端”，把分发多进程的父进程定义为“服务器”。

1.3.1 服务器初始化

  • 创建 Socket：服务器进程调用 socket() 系统调用。内核在进程的描述符表中分配一个最小可用索引（假设为 fd 3），并在内核空间创建一个对应的套接字结构。
  • 绑定与配置：通过 bind() 将 fd 3 与特定的 IP 地址和端口号关联。
  • 转换为监听状态：服务器调用 listen(3, ...)。此时，fd 3 的性质发生变化，成为监听描述符 (Listening Descriptor)。它不再负责数据传输，而是专门负责处理内核中 TCP 全连接队列里的连接请求。

1.3.2 客户端发起连接

  • 客户端初始化：客户端进程调用 socket() 创建自己的描述符（假设为 fd 5）。
  • 发起握手：客户端调用 connect(5, server_addr, ...)，内核协议栈向服务器发送 SYN 包（第一次握手）。
  • 协议栈处理：服务器内核在接收到 SYN 并完成 SYN-ACK 与 ACK（三次握手）后，将该连接从“半连接队列”移动到“已连接队列”。

1.3.3 连接的建立与分发

  • 描述符生成：服务器主进程调用 accept(3, ...)。该调用从已连接队列中取出一个条目，内核为此连接在描述符表中分配一个新的空位（假设为 fd 4）。
  • 职责分离：
    • fd 3（监听描述符）：继续保持监听状态，负责后续其他客户端的握手请求。
    • fd 4（已连接描述符）：代表一个具体的客户端 TCP 链接，负责该连接的数据读写。
  • 创建子进程：为了实现并发，服务器主进程调用 fork()。

1.3.4 并发处理中的描述符共享

  • 副本生成：根据 fork 机制，子进程获得父进程描述符表的完整副本。此时，子进程的描述符表中同样存在指向同一个内核文件表项的 fd 3 和 fd 4。
  • 关闭冗余句柄：
    • 子进程行为：立即执行 close(3)。因为它只负责处理当前连接，不需要监听新请求。它通过 fd 4 与客户端进行 I/O 交互。
    • 父进程行为：立即执行 close(4)。因为它已将该连接的控制权“交给”了子进程，它需要腾出资源去继续监听 fd 3。
  • 引用计数管理：内核中对应 fd 4 的打开文件表项的引用计数（refcnt）最初为 2。只有当父子进程都执行了 close 后，refcnt 归零，该物理连接才会真正被销毁。

1.3.5 父进程调度不同客户端请求

此处父进程相当于调度中心，通过将不同的描述符分发给不同子进程，分别处理不同客户端需求。

开发者笔记：在这个模型中，父进程通过描述符分发任务，本质上是“任务状态与执行环境的完全剥离”。父进程只管“描述符/任务包”，子进程在封闭环境里“处理计算”。这种架构天然支持多核并行，因为每个进程都是独立的，这为我们后面解决 Python 的 GIL 问题提供了理论基础。

1.4 线程：轻量级的逻辑流与共享

如果说进程是操作系统分配资源的最小单位，那么线程就是 CPU 调度的最小单位。

1.4.1 线程的上下文

与进程拥有庞大的私有地址空间不同，线程非常轻量，只拥有维持运行所必须的极少量私有数据：

  • 线程 ID (TID)：每个线程的唯一标识。
  • 程序计数器 (PC)：记录当前执行到的指令位置。
  • 寄存器与栈指针：存储临时变量和函数调用记录。

1.4.2 共享、透明的内存空间

在同一个进程内的多个线程，就像是在同一个办公室里共用资料库的员工。它们共享：

  • 整个虚拟地址空间：包括只读代码段、读/写数据段、以及堆。这意味着一个线程创建的对象，其他线程可以直接读写。
  • 打开的文件集合：所有文件描述符对所有线程是完全透明共享的。

开发者笔记：

  • 低开销及代价：线程创建比进程快得多，因为不需要复制页表（进程私有地址空间在触发写操作时才需要复制；只读场景会触发 COW 延迟复制）。但这种“零距离”共享意味着一个线程写坏了内存，整个进程都会挂掉。
  • 通信零成本：线程间通信不需要像多进程那样搞 IPC（管道/队列），直接读写全局变量即可。但也正是这种便利，我们需要花费更多精力和运行时间去处理“竞争”。

1.5 变量映射与同步风险

由于线程间内存是共用的，资源管理变得极其复杂。

  • 竞争条件：由于多线程可以同时访问相同内存，即使是 count += 1 这样简单的操作，在 CPU 层面也涉及“读-改-写”三步。如果没有同步，两个线程可能同时读到旧值，导致更新丢失。
  • 同步元语：为了解决竞争，必须引入互斥锁。（更详细内容参见 CSAPP 信号量一节）

开发者笔记：

  • 锁争用：在一个进程内开启多个线程时，如果它们都在抢同一把锁，多个线程会处于阻塞状态。并行代码实际上退化成了串行。
  • 不可见的性能税：加锁、解锁，以及内核在不同线程间疯狂切换，会消耗大量 CPU 时钟周期。

1.6 Python 的特殊枷锁：GIL (Global Interpreter Lock)

这把 GIL 锁就是 1.5 中提到的互斥锁，也是我在实验中遇到的耗时飙升的底层根源：

  • 核心限制：为了内存安全，CPython 解释器要求在任何时刻，一个进程中只有一个线程能持有 GIL 执行 Python 字节码。
  • CPU 密集型困境：在进行计算（涉及大量正则匹配、HTML 解析）时，线程会死死攥住 GIL 不放。
  • 性能退化：多个线程抢夺唯一的 GIL，产生巨大的上下文切换开销。这种“伪并行”不仅无法利用多核 CPU，反而因为内耗导致单位样本处理速度显著退化。

开发者笔记：

  • 识别任务类型：这是方法论的核心。如果你的任务是 time.sleep() 或等待网络 API 返回（I/O 密集），多线程是神药；如果是疯狂算逻辑的任务（CPU 密集），多线程就是毒药。

1.7 协程：用户态的“时间管理大师”

如果说进程是操作系统的资源单位，线程是 CPU 的调度单位，那么协程（Coroutine）则是程序员手中的“逻辑流转换艺术”。从定义角度看，协程是程序员手动在一个线程或进程中开启、可自由调度的逻辑流，其转换发生在用户态而非线程切换的内核态，因此可以节省极大的切换开销。本质来说，线程和进程是“人多力量大”，而协程则通过异步等待更高效地利用 CPU。

1.7.1 底层原理：非本地跳转与 I/O 多路复用

虽然 CSAPP 目录中没有直接出现“协程”二字，但其核心技术栈早已在书中埋下伏笔：

  • 执行流切换（User-level Context Switch）：利用 CSAPP 第 8 章提到的非本地跳转（Nonlocal Jumps）原理（类似 setjmp/longjmp），协程在用户态保存和恢复寄存器上下文。这种切换不经过内核，开销极小。
  • 非阻塞 I/O（Non-blocking I/O）：这是协程的灵魂。它通过 CSAPP 第 12 章介绍的 I/O 多路复用 技术（如 epoll）来监控文件描述符。

1.7.2 协作式并发 vs 抢占式并发

  • 线程（抢占式）：内核像严厉的监考老师，随时可能掐断你的执行流去换另一个人。在这种模型下，每个线程在等待 I/O 时只能“死等”，即阻塞。
  • 协程（协作式）：协程之间是“礼让”关系。通过 await 关键字，协程在遇到 I/O 等待时会主动说：“我现在要等数据，先挂起（yield）自己，大家先用 CPU。” 这种异步机制确保了单线程也能处理成千上万的连接。

1.7.3 开发者笔记

  • 真异步与假并行：协程在 Python 中依然受单核 GIL 限制，它不是为了物理上的“同时算”，而是为了在 I/O 等待空隙里“高效干活”。
  • 资源利用率：线程的栈通常以 MB 计，而协程的初始栈仅为 KB 级别。这决定了你可以轻松开启 10,000 个协程，却无法开启 10,000 个线程。

实例分析：从“几乎卡死”到“秒速处理”

在昨天的场景中，优化的核心任务大致可以理解为：对 2w 条模型输出进行归一化，并根据模型输出和 gt 计算某种得分。这是一个典型的计算密集型（CPU-bound）任务，对 CPU 算力有着极高的连续需求。

2.1 演进路线：三种计算模型的客观实验

在尝试中我先后用了以下三种方法，分别对应不同的系统级处理逻辑与资源分配方式。

阶段 A：串行流

  • 运行机制：采用标准 for row in rows 循环。程序在单一逻辑控制流下运行，指令按序进入 CPU。
  • 资源利用：仅占用 1 个 CPU 核心，其余 15 核处于“围观”状态。
  • 实际表现：
    • 平均耗时：1.76s / 样本。
    • 评价：逻辑最简单，但面对近 2 万条数据，预估总耗时超过 8 小时，无法满足快速迭代需求。

阶段 B：多线程

  • 尝试：使用 ThreadPoolExecutor，试图通过 64 个并发线程切分任务，并为每个线程准备私有计算实例用来计算 gt 和模型回复之间的匹配程度。

    这里我当时天真地以为 max_workers 开得越大就应该越快。

  • 核心矛盾（GIL 枷锁）：
    • 计算涉及大量正则匹配与矩阵运算，属于 Python 字节码密集操作，无法触发 GIL 自动释放。
    • 16 个物理核心上的 64 个线程在内核中疯狂争夺唯一的 GIL 锁。
  • 实际表现：
    • 平均耗时：96.1926s / 样本。
    • 现象：性能发生严重退化，单条耗时相比串行反而慢了约 200 倍。系统 99% 的能量消耗在“为了抢锁而进行的无效上下文切换”上。
    • 分析：在 CPU 密集任务中，由于线程无法主动交出锁，OS 会频繁强制切换线程。每一次切换都要保存/恢复寄存器、刷新缓存，这在 64 线程高并发下会产生“惊群效应”。

阶段 C：多进程 - 真正释放多核福利

  • 策略：切换为 ProcessPoolExecutor，开启 16 个独立 worker 进程。
  • 技术优势（内核级对齐）：
    • 绕过 GIL：每个进程拥有独立 Python 解释器和 GIL，16 核真正实现了真并行。
    • 内存优化：利用 initializer 进行进程级一次性初始化，并配合 COW（写时复制） 机制，确保高效资源利用。
    • I/O 收口：针对 File Offset 共享 风险，设计“子进程只传变量，主进程统一写盘”的模式，规避并发写导致的文件损坏。
  • 实际表现：
    • 平均耗时：2.21s / 样本。
    • 吞吐量：内核同时启动 16 个进程，吞吐量约 0.14s / 样本，吞吐量显著提升，耗时分布恢复正常，整体处理速度相比串行提升约 10-12 倍。
    • 进程间通信：多进程单条耗时略增（1.7s -> 2.2s），主要来自主进程将数据 pickle 序列化后通过管道（Pipe）传输给子进程。

方法总结：多线程、多进程还是协程？

在进入具体选择逻辑之前，我们先达成一个共识：Python 并不是一门原生擅长并行计算的语言。

作为一门解释型“胶水语言”，Python 的核心优势在于逻辑调度和快速开发。由于 GIL（全局解释器锁） 的存在，Python 很难像 Go 或 Erlang 那样在语言层面实现极致的多核利用率。

但在现代工程实践中，我们通常采用“大脑（Python 逻辑调度）+ 肌肉（C/C++ 底层计算）”的架构：

  • 计算重心在 C 扩展：如 NumPy、PyTorch 这类底层由 C/C++ 编写的库，在执行重负载任务时会主动释放 GIL。此时，多线程也能跑出物理并行效果。
  • 计算重心在 Python 本身：如果是纯 Python 循环或逻辑处理，控制权始终在 Python 解释器手中，GIL 就是无法绕开的瓶颈。

3.1 核心判断矩阵

选择并发模型的第一步，是识别任务的“性能瓶颈”在哪里：

维度 多协程 (AsyncIO) 多线程 (Threading) 多进程 (Multiprocessing)
瓶颈定位 极高并发 I/O 少量并发 I/O CPU 密集型
典型场景 异步爬虫、高性能 Web 服务 快速脚本、调用释放 GIL 的 C 库 大模型计算、复杂正则匹配
通信成本 极低（单线程内共享） 低（共享内存） 高（需跨进程序列化/IPC）
Python 限制 受单核 GIL 限制 受单核 GIL 限制 绕开 GIL，真并行
底层原理 异步非阻塞（await） 同步阻塞（线程切换） 物理隔离（独立解释器）

3.2 决策算法：三步走指南

  1. 识别“计算重心”
    • 如果 CPU 大部分时间在等待（网络、磁盘），且并发量巨大 -> 多协程。
    • 如果代码在疯狂进行逻辑运算（算分、解析、匹配） -> 多进程。
  2. 检查“肌肉”是否释放 GIL
    • 调用 NumPy、PyTorch 等 C 扩展库时，它们通常会主动释放 GIL。此时即使是多线程也能跑出不错的并行效果。
  3. 评估通信代价
    • 多进程间传递大数据需要序列化（pickle），开销较大。推荐“分布式计算 + 主进程聚合”模式。

3.3 避坑避雷指南

  • 不要迷信“线程轻量”：在 CPU 密集任务面前，多线程锁竞争损耗远超它省下的那点内存。
  • 协程不是银弹：它解决的是“排队等待”效率，而不是“搬砖速度”。没有 await 挂起点的计算任务用协程并不会加速。
  • 调库不等于绕开 GIL：如果调用的库是纯 Python 写的，它依然受限于单核 GIL。
  • 警惕文件偏移量共享：始终坚持由主进程单点写盘，或为每个子进程分配独立临时文件。
